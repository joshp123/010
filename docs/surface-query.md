# Exact measured surface queries

Written by AI on 2026-10-24 by model GPT-6.

`public/surface-query.js` accelerates the existing vertical placement query for observed transit and simulated road traffic. It does not change either data source, advance vehicles, or generate terrain heights. Source bridge decks retain priority over native ground and compact green terrain. The previous height interval and minimum surface-normal Y remain unchanged.

The source mesh is indexed into 32 m cells in the rendered local XZ frame. Each cell stores Uint32 offsets into the original triangle index. Queries run Three.js `Ray.intersectTriangle` on those exact current triangles and return the highest acceptable intersection. Source positions, transforms and normals are never resampled or quantized. Very broad triangles occupy a separate candidate list when their bounds cover more than 64 cells, limiting index allocation for large water polygons.

`setModels(models)` tracks the current visible meshes. Geometry replacement, index/position replacement or version changes, draw-range changes and world-transform changes rebuild the affected mesh index. This runs after source fusion, so bridge reconciliation uses the resulting geometry. Visibility changes and unloading release old records. `heightAt(x,z,min,max)` returns the exact surface height or null. A null result retains the existing explicitly graphical fallback. Disposal clears the CPU index; the module creates no GPU resources.

Per-layer `getDiagnostics().surfaceQueries` reports builds, cumulative build time, queries, tested triangles, current meshes/triangles and typed index bytes. The byte count excludes ordinary JavaScript Map/object overhead. Original source buffers are referenced, not duplicated.

The triggering integrated profile is `work/visual-qa/centre-night-load.cpuprofile`: broad raycasts dominated the load, while native ground filtering and bridge fusion were much smaller contributors. An actual native Erasmus comparison exercised 618 query positions before and after the current source-fusion operation. Every hit/miss and height matched the old Raycaster within 0.1 micrometre. Unfused queries took approximately 14 ms against 402 ms; fused queries took 19 ms against 420 ms in Node. Building the 18,500-triangle index took 4–5 ms and about 107 KB of typed offsets. The check also exercised geometry replacement and removal.

The integrated in-app browser check at the centre, 900 m span, night, settled in 5,242 ms against 21,933 ms before: approximately 4.2 times faster. First buildings appeared in 3,871 ms against 3,537 ms. This was a warm-cache localhost comparison on one machine, not a 100 ms loading claim or a device-independent benchmark. Ground indexing took 227 ms cumulatively across 71 builds for 55 current meshes (815,000 triangles, 4.45 MB typed index); 37,000 queries examined 2.95 million candidate triangles. The rendered night view was inspected with native geometry retained. Evidence: `work/visual-qa/centre-night-accelerated.cpuprofile` and `centre-night-accelerated.jpg`.

To reproduce the browser comparison, load the same centre at 900 m span at night, record a Performance CPU profile from reload until readiness settles, and inspect `getDiagnostics().surfaceQueries` and the rendered map. Use the same cache state and machine for both revisions. Exact-query scope is static triangle meshes with the current double-sided source materials. Skinned or instanced surfaces and mixed per-group material sidedness are not supported; none are used by the three queried terrain layers. Placement remains bounded by whichever source tiles are currently loaded.
