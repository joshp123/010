# Measured performance

Written by AI on 2026-10-24 by model GPT-6.

The map retains native source geometry. These checks measure local and public deployments in the in-app browser, with cache conditions stated separately. They do not establish physical phone performance or a universal 100 ms response time.

The first public-domain check on 2026-10-24 at `010.jjpcodes.com`, 900 m centre view at night, submitted buildings at 5.37 s and settled at 11.69 s. This was the first visit to that origin, but external native tiles could already be in the browser cache. A public Kralingen pan at a 390 × 844 viewport recorded eight input-to-render submissions: median 12.7 ms, p95 14.7 ms, with zero pending/refused tiles after settling. No CPU or network throttling was applied. These measurements distinguish responsive camera movement from much slower detail streaming; the 100 ms loading aspiration has not been achieved.

After compressed delivery was published, a 1440 × 900 centre/night check with browser caching bypassed submitted buildings at 6.34 s and settled at 21.34 s, with zero pending/refused tiles or loading errors. This differs from the earlier cache condition and is not a before/after speed comparison. Twenty-five prepared-model sidecars loaded successfully. The hosted Erasmus model was 21,589 bytes and decoded to all 58,852 original bytes with exact SHA-256 parity. The slowest requests were native Rotterdam ground/bridge tiles, around 12–16 seconds each; those are outside the prepared-file compression path. Browser caching was restored after the check. Evidence is retained in `work/visual-qa/published-cache-bypass.json` and `published-final-night.jpg` on the SSD.

The final public release, including building priority and the attachment correction, repeated that cache-bypassed centre/night view: first buildings at 5.76 s, full detail at 18.80 s, zero pending/refused tiles or errors. All 44 duplicate structures were suppressed and the ground retained the same 814,997 triangles as the correctly reconciled baseline. This remains far above the loading aspiration. The final local pan recorded eight input-to-render submissions with median 11.8 ms and p95 15.6 ms. Neither result establishes physical-phone performance. Final public diagnostics and the inspected screenshot are retained as `work/visual-qa/published-final-corrected.json` and `.jpg`; browser caching was restored after verification.

The two slowest native ground/bridge files contain no images, textures or UV coordinates: geometry occupies 94.6% and 99.9% of their decoded bytes. Both already transfer with gzip (1.41 MB and 1.27 MB). Two simultaneous direct downloads subsequently took about 1.1 s each, so the browser result does not establish a consistently slow origin; concurrent transfer and browser scheduling need separate measurement. Mirroring the municipality's native models cannot fit the roughly 8 MiB remaining in the current Sites publication archive.

The renderer's shared queue has ten slots per origin, but its default fetch releases a slot at response headers rather than after the binary body. An experiment held the slot through the complete body. The actual queue/HTTP fixture confirmed the intended concurrency, but browser checks showed worse full-detail arrival in Hoogvliet and the port despite a centre improvement, so that change was rejected. The retained change simply gives buildings priority over detailed ground. It does not change geometry or the loader. Changing arrival order also exposed a bridge-reconciliation cache defect; world-transform invalidation fixes it independently of queue priority. See [source reconciliation](data-sources.md#conflicting-bridge-surfaces).

During dragging, pinching, rotation and wheel bursts, the camera and rendering continue using the currently selected source tiles. Tile selection, bridge reconciliation, surface indexing and road reprojection resume after release and 120 ms without input. A long gesture into unloaded territory can therefore show cartographic fallback until it ends. Full detail then loads normally; deferred selection reports pending readiness, and full-detail export bypasses this deferral. Already-running source decoding can still consume CPU during input.

Prepared model delivery uses gzip sidecars generated by `scripts/compress-model-assets.mjs` after `vinext build`. Raw GLBs remain unchanged in `public/` and in build output; the extra `.glb.gz` files exist only in `dist/client/data/`. Compression is limited to industrial structures, lamps, streets and bridge surfaces; one exported directory set is shared by the builder and loader. Green terrain and industrial ground use the raw loader without sidecar requests. This selection keeps the expanded publication archive within Sites’ 256 MiB limit, which the all-model sidecars exceeded. The loader's small `fetchData` plugin requests these sidecars only for same-origin `/data/*.glb` URLs within that shared selection and uses native `DecompressionStream` before the existing Three.js parser. A missing sidecar falls back to the original GLB for source previews; browsers without native decompression use the default raw loader. External native Rotterdam tiles, cancellation signals, geometry and model URLs in source manifests are unchanged. No compression dependency or proxy API is added. Sidecars increase the deployment archive size; they reduce browser transfer, not geometry decoding cost.

The preceding `_headers` approach worked in local Wrangler but the deployed Sites responses did not apply those headers. The ineffective source file was removed. This delivery path therefore does not rely on custom static response headers; Sites serves the gzip bytes as an ordinary file. Framework-generated cache headers and existing model cache lifetimes are unchanged.

An actual HTTP fixture exercised the vendored 3D Tiles `fetchData` hook and GLTFLoader. Complete build files total 257,112,240 bytes, retaining raw browser fallbacks and no excluded-directory sidecars.
